<objective>
Build the policy engine PRIMITIVE: a `policies` SQLite table (migration 176) and a
`PolicyService.evaluate()` that stacks rows across server → team → session scopes,
evaluates the SESSION (stricter) scope FIRST, and short-circuits on the first DENY.
This is the foundation every later plan in the phase depends on.

Purpose: Satisfy SC1 — the locked stacking-order invariant (session DENY short-circuits a
server ALLOW), anchored on the SESSION scope per the standing session-not-bot rule.
Output: `policy_service.py` (evaluate + row reads + CRUD helpers + `PolicyDenied`), migration
176 with a registry entry, and two unit-test files.
Research basis: 23-RESEARCH.md Pattern 2 (evaluator shape) + Recommendation 3 (stacking order),
modeled on `BudgetService` (classmethod service) and `budget_service.py:340` verdict shape.
</objective>

<feature>
  <name>PolicyService.evaluate stacking + short-circuit (SC1)</name>
  <files>backend/app/services/policy_service.py, backend/tests/test_policy_evaluator.py</files>
  <behavior>
    PolicyService.evaluate(*, session_id, team_id=None, action: dict) -> dict (PolicyVerdict).
    Iterate scopes in order [("session", session_id), ("team", team_id), ("server", None)].
    For each scope, read enabled rows via _rows_for(scope, scope_id) ORDER BY priority DESC.
    Evaluate each row with _eval_row(row, action) -> (decision, reason); in THIS plan _eval_row
    returns the row's stored `effect` verbatim (builtins land in 23-02).
    Cases (input -> expected output):
      - server ALLOW row + session DENY row -> {"decision":"deny","scope":"session", policy_id=<session row id>}
        AND the server scope is NEVER read (assert _rows_for not called with scope="server", e.g. via spy)
      - session ASK row + server ALLOW row -> {"decision":"ask","scope":"session"}
      - only a server ALLOW row -> {"decision":"allow","scope":None? or "server"} (allow fall-through; ALLOW rows do not short-circuit — default ALLOW returns scope=None, an explicit allow row is fine to ignore)
      - no rows at all -> {"decision":"allow","policy_id":None,"kind":None,"scope":None}
      - team DENY (no session row) -> {"decision":"deny","scope":"team"}
  </behavior>
  <implementation>
    - Classmethod service (matches BudgetService/ExecutionService). No instance state.
    - PolicyVerdict is a plain dict: {"decision": "allow"|"deny"|"ask", "policy_id": str|None,
      "kind": str|None, "reason": str, "scope": str|None}.
    - evaluate(): track first ASK in `ask_verdict`; return immediately on first DENY; after all
      scopes, return ask_verdict or the default ALLOW. Skip a scope whose scope_id is None EXCEPT
      "server" (server is the sentinel scope with scope_id IS NULL).
    - _rows_for(scope, scope_id): SELECT * FROM policies WHERE scope=? AND
      (scope_id=? OR (? IS NULL AND scope_id IS NULL)) AND enabled=1 ORDER BY priority DESC;
      parse `params` JSON into a dict on each row.
    - _eval_row(row, action): for this plan, return (row["effect"], f"policy {row['id']} effect").
      Leave a clear extension seam (a dispatch dict `_BUILTINS = {}` referenced by kind) for 23-02.
    - Add `class PolicyDenied(Exception)` for enforcement plans to raise (23-03 imports it).
    - Add CRUD helpers used by later plans: create_policy(...)/list_policies(scope=None)/
      get_policy(id)/update_policy(id, **f)/delete_policy(id); ids prefixed-random `pol-` + 6 chars
      (reuse the existing id-generation helper used by other services — grep for the prefixed-id
      generator; do NOT hand-roll a new random scheme). Use get_connection() for all DB access.
    - Tests use the isolated_db fixture. To prove short-circuit, monkeypatch/spy PolicyService._rows_for
      to record the scopes it was called with and assert "server" never appears after a session DENY.
  </implementation>
</feature>
