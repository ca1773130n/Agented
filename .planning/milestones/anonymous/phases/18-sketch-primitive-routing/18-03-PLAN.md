<objective>

it into `route_sketch` as the `primitive_generator` dispatch target, plus a
self-contained undo endpoint.

`create_and_bind_and_materialize`; improve fuzzy-resolves over bound
primitives, applies an old→new delta, re-materializes, and falls back to

<decision>
RESEARCH Open Question 1 — `create_skill` has no entry in `_CREATE_FNS` (the
atomic API raises ValueError for "skill"). DECISION (autonomous mode): the
`create_skill` action routes to `add_user_skill` (db/skills.py) to create the
user-skill row, then adds a forge binding ("skill" is in
VALID_FORGE_BINDING_KINDS) and materializes — i.e. a dedicated skill branch
inside PrimitiveForgeService, NOT a push through create_and_bind_and_materialize.
Undo for a created skill = remove_binding + delete_user_skill +
re-materialize. This keeps all 7 actions reachable while respecting Phase 17's
exclusion of skill from the atomic create map.

RESEARCH Open Question 2 — "per-kind generation to a complete draft": for v1
the payload (name/content) is built deterministically from the sketch
title/body, with an injectable draft source (param/monkeypatch) so an LLM draft
can be substituted without a live LLM in tests. When wired live, the LLM-draft
seam uses the SAME litellm-model-string mechanism as 18-01 (a per-kind
default-model map resolving `model_override or _LLM_MODELS.get(provider_kind)`
to a litellm model STRING passed to `litellm.completion(model=...)`), NOT
`resolve_llm_cmd` (which returns a subprocess argv template incompatible with
litellm). Per the 4-backend house rule, any LLM draft path accepts
{provider_kind, model_override} — never claude-only.
</decision>
