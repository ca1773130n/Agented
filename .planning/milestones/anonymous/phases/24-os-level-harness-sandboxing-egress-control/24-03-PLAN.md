<objective>
Wire the sandbox prefix (Plan 01) + egress proxy (Plan 02) into the live harness launch, and gate it with the Phase-23 `enforce_sandbox` policy (REQ-31/32, crit 1/2/4). At the single `execution_service` chokepoint — where `stdbuf` is already prepended (~L617-621), right before `subprocess.Popen` (~L767) — prepend `build_sandbox_prefix(...)`, start an egress proxy and inject `proxy_env` into `build_subprocess_env`, set `PolicyContext.sandbox_enabled` from the REAL `sandboxed` flag, then call `enforce_action` BEFORE Popen so an `enforce_sandbox` DENY refuses an unsandboxed launch. Then sweep the other five harness Popen sites through the same builder (defense-in-depth).

Purpose: every live harness subprocess runs sandboxed behind deny-by-default egress, and a policy DENY can stop an unsandboxed launch — the security spine of the phase.
Output: edits to execution_service/execution_runner + 5 swept services + the gate + sweep tests.
Research basis: 24-RESEARCH.md §Confirmed Integration Points (exact lines), §Phase-23 seam, Pitfall 1 (sweep), Pitfall 3 (env best-effort).
SECURITY PHASE: do NOT simplify away the enforce_sandbox gate or deny-by-default egress.
</objective>
