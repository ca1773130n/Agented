# v0.6.0 — Performance audit + targeted fixes (design)

First milestone of v0.6.x. Establish performance measurement
infrastructure, identify the actual bottlenecks, and ship the
top high-impact fixes. Defer Redis / workers>1 unless profiling
demands it.

## Goals

- Operator can run `just profile` and get p50/p95 latency per
  endpoint, and `just db-audit` to inspect index coverage on the
  hot paths.
- Server emits `Server-Timing` HTTP response headers so a browser /
  test harness can see per-request cost without server-side
  log digging.
- Ship the v0.5.x deferred wins that profiling-or-audit reveals:
  - Token-indexed sessions lookup (v0.5.12 deferred — replaces the
    full-table scan in `get_session_by_token`).
  - Frontend vendor chunk splitting (vite warns about >500KB chunks
    on every build).
  - DB indices on hot-path queries identified by `db_audit.py`.
- A `BASELINE.md` doc records the p50/p95 numbers BEFORE and AFTER
  so future passes (v0.6.0.x) have a quantified reference.

## Non-goals

- Redis-backed shared state (workers>1 readiness). Stay on
  workers=1; if profiling shows CPU saturation, that's a separate
  milestone.
- Token bucket / sliding window rate limit (v0.5.14 fixed-window
  is sufficient).
- Live runtime profiling dashboard. Out of scope; the
  `Server-Timing` header + the `profile.py` CLI are enough.

## Architecture

```
Layer 1 — measurement
  scripts/profile.py             one-shot endpoint p50/p95 profiler
  scripts/db_audit.py            EXPLAIN QUERY PLAN + index coverage
  app_litestar/middleware.py     PerformanceMiddleware emits Server-Timing

Layer 2 — targeted fixes
  app/db/sessions.py             token-indexed lookup (replace scan)
  app/db/migrations.py           migration 111 — sessions(token) index +
                                 rotated_from_token covering index
  frontend/vite.config.ts        manualChunks for big vendor bundles

Layer 3 — documentation
  docs/perf/BASELINE.md          before/after p50/p95 + vendor chunks
  justfile                       profile, db-audit recipes
```

## Components

### `scripts/profile.py`

CLI that hits a running server N times per endpoint and aggregates
p50/p95/min/max. Usage:

```bash
just profile              # default: localhost:20000, 50 reqs each
just profile -- --base http://staging:20000 --requests 200
```

Endpoints sampled:
- `GET /health/liveness` — baseline (should be sub-ms)
- `GET /health/readiness` — DB-touching baseline
- `GET /admin/agents` — list (RBAC + DB)
- `GET /admin/products` — list (RBAC + DB)
- `GET /admin/auth/session-events` — recently-added (v0.5.12 audit)
- (operator can extend via `--endpoints` flag)

Output: JSON summary on stdout for scripted callers; human-readable
table on stderr.

### `scripts/db_audit.py`

CLI that inspects the SQLite schema:
- Lists all tables + their indices via `PRAGMA index_list`.
- Runs `EXPLAIN QUERY PLAN` on a hand-picked set of the codebase's
  hot queries (sessions lookup, role lookup, agent list, etc.).
- Flags any query that uses `SCAN TABLE` (full scan) instead of
  `SEARCH TABLE` (index hit).

Output: JSON summary on stdout; table on stderr.

### `PerformanceMiddleware`

ASGI middleware that wraps the `next_app` call to time the
handler, then injects a `Server-Timing` header on response start
(format: `Server-Timing: app;dur=42.3`). Adds ≤1ms overhead on
every request.

Registers AFTER all other middleware so it sees the full request
processing time. Test that it doesn't break SSE responses.

### Token-indexed sessions lookup

The v0.5.12 `get_session_by_token` does `SELECT * FROM sessions`
then iterates with `hmac.compare_digest`. For typical operator
session counts (low hundreds) this is fine, but it's O(n) per
authenticated request. Migration 111 adds:
- `CREATE UNIQUE INDEX idx_sessions_token ON sessions(token)`
- `CREATE INDEX idx_sessions_user_id_active ON sessions(user_id, revoked_at)`

`get_session_by_token` is rewritten to:
1. `SELECT * FROM sessions WHERE token = ? OR rotated_from_token = ?`
2. Apply `hmac.compare_digest` to the matched row(s) to preserve
   constant-time comparison post-lookup.
3. Idle/expired/revoked checks unchanged.

This preserves the no-early-return timing characteristics from
v0.5.12 round-3 (compares run on every matched row before
deciding) while reducing the lookup cost from O(n) to O(log n).

### Vite manual chunks

Current `just build` warns:
- `vendor-core` 2.86 MB
- `ai-accounts-vue-styled` 1.09 MB
- `vendor-vue-flow` 261 KB

Split into named chunks via `vite.config.ts:build.rollupOptions.output.manualChunks`:
- `vendor-vue` — Vue runtime + Pinia (if used)
- `vendor-router` — vue-router
- `vendor-flow` — vue-flow + dagre
- `vendor-styled` — ai-accounts-vue-styled
- `vendor-core` — everything else

Goal: no chunk > 1MB (the >500KB warning is acceptable for vendor
splits in dev, but let's at least cap the worst offender).

## Data flow

```
just profile
  ↓
scripts/profile.py
  - For each endpoint: N sequential GET requests
  - Capture status + Server-Timing header app duration
  - Aggregate min/p50/p95/max per endpoint
  - JSON to stdout

just db-audit
  ↓
scripts/db_audit.py
  - List all tables + indices
  - EXPLAIN QUERY PLAN for hot queries
  - Flag SCAN TABLE usage
  - JSON to stdout

(separately) just build
  ↓
After v0.6.0 fixes: vendor chunks split, no >500KB warning on
the chunks we control.
```

## Error handling

- `profile.py`: server unreachable → exit 1 with clear message;
  one endpoint failing doesn't abort the whole run, just records
  errors in the per-endpoint output.
- `db_audit.py`: missing DB → exit 1; per-query EXPLAIN failure
  logs WARN, records `error: ...` in the entry, continues.
- `PerformanceMiddleware`: never raises; if header injection
  fails, the request still completes.

## Testing

`backend/tests/test_perf_middleware.py` — 3 tests:
1. Server-Timing header is present on a normal response.
2. Header value parseable as `app;dur=<float>` with positive ms.
3. SSE / chunked responses still work (header on initial chunk only).

`backend/tests/test_db_audit.py` — 4 tests:
1. `audit_indices` lists all known tables.
2. `explain_query` returns SCAN/SEARCH classification.
3. CLI exits 0 on healthy schema.
4. CLI flags SCAN-only queries on hot paths.

`backend/tests/test_profile.py` — 3 tests (CLI behavior):
1. Aggregator computes correct p50/p95 from synthetic data.
2. CLI exits nonzero when server unreachable.
3. JSON output structure is stable.

`backend/tests/test_sessions_lookup.py` — 3 tests:
1. Lookup uses index path (verified via EXPLAIN QUERY PLAN).
2. Token rotation case still resolves correctly via index.
3. Constant-time comparison still applied (no early return on
   non-match within the indexed result set).

Frontend: visual inspection of `npm run build` output — the existing
`just build` already shows chunk sizes; no test needed.

## Conventions

- Scripts in `backend/scripts/`, tests in `backend/tests/`.
- New env vars: none. Profiling is on-demand; middleware is
  always-on but no-config.
- `BASELINE.md` lives in `docs/perf/`.
- Migration version: 111.

## Out of scope

- Always-on profiling that writes per-request samples to a DB.
- A perf dashboard UI.
- Redis-backed scheduler / SSE / message bus.
- DB profiling at the ORM level (no ORM in use).
- Frontend code-splitting for route-level lazy loading (separate
  concern; v0.6.0 only does vendor splits).
