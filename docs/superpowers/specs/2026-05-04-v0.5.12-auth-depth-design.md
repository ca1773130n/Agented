# v0.5.12 — Auth depth (RBAC enforcement + session lifecycle hardening)

**Date:** 2026-05-04
**Milestone target:** v0.5.12 (E-A piece — production hardening)
**Status:** design awaiting user review

## Context

Per the original E decomposition, v0.5.12 ships **A — auth depth**:
RBAC enforcement on routes, session lifecycle hardening, and (per
Q1 decision) drops the OAuth-refresh sub-piece since operator auth
isn't OAuth-based — that work would belong to ai-accounts and isn't
Agented's concern.

Existing state inventory:

- **RBAC roles** — 4 levels defined (`viewer / operator / editor /
  admin`) per `UserRoleCreate.role`. `app/db/rbac.py` (274 lines)
  handles user_role CRUD.
- **ApiKeyMiddleware** at `app_litestar/middleware.py:117` — only
  authenticates (valid key OR session); does NOT authorize by role.
  Any authenticated principal can call any route.
- **Sessions** at `app/db/sessions.py` (101 lines) — create / get
  by token / revoke / purge_expired. Default lifetime, no idle
  timeout, no sliding refresh, no rotation, no revocation hooks
  on role change.
- **OAuth** — only used for AI backend accounts (ai-accounts repo);
  not relevant to operator auth.

What's missing / weak:

1. No per-route role checks. A viewer can DELETE.
2. Sessions have absolute lifetime but no idle timeout. A logged-in
   tab open for hours past last interaction can keep working until
   absolute expiry.
3. No sliding refresh — sessions silently expire even if actively
   used.
4. No token rotation — a stolen bearer token works for the full
   absolute lifetime.
5. Rotating a user's API key (`rotate_user_role(role_id)`) leaves
   that user's existing bearer sessions live.
6. No audit log of session lifecycle events.

## Goal

1. Add RBAC enforcement on all `/api/*` and `/admin/*` routes via
   coarse middleware defaults plus per-route overrides for
   sensitive operations.
2. Refactor `app/db/sessions.py` to support idle timeout, sliding
   refresh, token rotation, and revocation hooks.
3. Add `session_events` audit table and insert helpers; log every
   lifecycle event from middleware and sessions/rbac modules.
4. Update the frontend API client to consume the rotated session
   token from a response header on every authenticated response.

## Non-goals

- **OAuth refresh** for operator auth — operator auth is API-key +
  session, not OAuth (per Q1).
- **Observability UI for session_events** — backend-queryable in
  v0.5.12 via a new admin route; the UI surface (similar to v0.5.10
  traces page) is a v0.5.13+ candidate.
- **Multi-factor authentication.**
- **Per-resource ACLs** (per-agent / per-team granular permissions)
  — RBAC stops at role tier.
- **Frontend session-management UI** ("list my sessions / revoke
  this one"). Useful follow-up; out of scope.
- **CSRF tokens.** Bearer-session pattern is not vulnerable to CSRF
  in the standard sense; threat-model-driven separate milestone if
  the deployment context warrants it.

## Architecture

Backend-heavy. Frontend gets one focused change (token rotation
handler in `services/api/client.ts`).

### Sub-systems

1. **RBAC enforcement** — extend `ApiKeyMiddleware` with a
   `(method, prefix) → required_role` table for coarse defaults;
   add `requires_role(...)` Litestar guard for per-route overrides.
2. **Session lifecycle** — schema additions on `sessions` table +
   new functions in `app/db/sessions.py` for rotate / refresh /
   revoke-by-user_id / mark-revoked-by-reason. Middleware orchestrates
   per-request.
3. **Audit log** — new `session_events` table; insert helpers in
   `app/db/session_events.py`; called from middleware, sessions
   module, rbac module.

## Component design

### Coarse role-required table

```python
# app_litestar/auth_guards.py

ROLE_RANK = {"viewer": 0, "operator": 1, "editor": 2, "admin": 3}

ROLE_REQUIRED: dict[tuple[str, str], str] = {
    ("GET",    "/api/"):    "viewer",
    ("GET",    "/admin/"):  "viewer",
    ("POST",   "/admin/"):  "editor",
    ("PUT",    "/admin/"):  "editor",
    ("PATCH",  "/admin/"):  "editor",
    ("DELETE", "/admin/"):  "admin",
}

# Public allowlist (bypasses role check after authentication).
PUBLIC_PATHS = ("/health/", "/docs", "/schema", "/admin/auth/login")

def required_role(method: str, path: str) -> Optional[str]:
    """Return required role for (method, path), or None if public."""
    for prefix in PUBLIC_PATHS:
        if path.startswith(prefix):
            return None
    for (m, p), role in ROLE_REQUIRED.items():
        if method == m and path.startswith(p):
            return role
    return None  # default-public for unmapped paths is intentional
```

The middleware composes this with `get_role_for_api_key(api_key)`
and `get_session_user(token).role` to produce the effective check.

### Per-route guard

```python
# app_litestar/auth_guards.py

def requires_role(min_role: str) -> Guard:
    """Litestar guard factory for per-route role overrides."""
    def guard(connection, _route_handler) -> None:
        principal = connection.scope["state"].get("principal")
        if principal is None:
            raise PermissionDeniedException(detail="not authenticated")
        if ROLE_RANK[principal["role"]] < ROLE_RANK[min_role]:
            raise PermissionDeniedException(detail=f"requires {min_role}")
    return guard
```

Initial per-route override list (audit-driven, ~10 routes):

- `POST /admin/users/:role_id/role` → `admin`
- `POST /admin/users/:role_id/rotate` → `admin`
- `DELETE /admin/users/:role_id` → `admin`
- `POST /admin/users/:user_id/sessions/revoke` → `admin`
- `POST /admin/setup/bundle-install` (touches subprocess) → `admin`
- `POST /admin/cliproxy/install` → `admin`
- `DELETE /admin/agents/:id/memory/threads/:thread_id` → `editor`
  (cleanup, not strictly destructive per coarse rule but worth
  bumping; coarse says `admin` because of DELETE — actually this
  one is *less* than coarse, so it stays at coarse default `admin`.
  No override needed; left here to surface the audit thinking.)

The audit-driven list will be finalized during implementation by
walking each route file and deciding per route. This list is
illustrative; the implementation phase produces the actual
overrides.

`revoked_at = NULL` (active by default).

### Session lifecycle behavior

Per authenticated request, the middleware orchestrates:

1. **Look up session by bearer token.** If not found → `401`. No
   event log (would create a side channel for token enumeration).
2. **Revoked check.** `revoked_at IS NOT NULL` → `401` + log
   `used_after_revocation` (event type).
3. **Absolute expiration.** `started_at + absolute_lifetime < now`
   → `401` + log `expired`.
4. **Idle expiration.** `last_activity_at + idle_lifetime < now` →
   `401` + log `idle_expired`.
5. **RBAC role check.** Per the coarse table or per-route guard.
   `403` if rank insufficient (but session itself stays valid; do
   NOT log a session event for 403 — RBAC is request-level, not
   session-level).
6. **Sliding refresh.** Update `last_activity_at = now`.
7. **Rotation.** Generate new token. Update sessions row:
   `token = new_token`, `rotated_from_token = old_token`,
   `last_activity_at = now`. Log `rotated` with metadata
   `{previous_token_hash: ...}`.
8. **Response header.** Add `X-New-Session-Token: <new>`.

Defaults (configurable via env vars or constants):

- `SESSION_ABSOLUTE_LIFETIME_HOURS = 24`
- `SESSION_IDLE_LIFETIME_MINUTES = 30`
- `SESSION_ROTATION_GRACE_SECONDS = 5` (server accepts the
  previous token for 5 seconds after rotation to handle
  concurrent-request races)

### Rotation grace window

Critical implementation detail. When rotation happens:
1. New token written to `sessions.token`
2. Old token preserved in `sessions.rotated_from_token`
3. `last_activity_at = now`

When a request arrives with a token, lookup logic:
1. First, `WHERE token = ?` → match → use this row
2. If no match, `WHERE rotated_from_token = ? AND last_activity_at > now - 5s` → match → use this row (do NOT rotate again on this request; the client must catch up)

After 5 seconds, the rotated_from_token is no longer accepted. This
closes the parallel-request race without expanding the attack
surface meaningfully (5-second window is shorter than typical
network round-trip delays for stolen-token replay scenarios).

### Revocation hooks

Three triggers for `revoked_at` write:

1. **`update_user_role(role_id, new_role)`** — call
   `revoke_user_sessions(user_id, reason='role_change')`.
2. **`rotate_user_role(role_id)`** — call
   `revoke_user_sessions(user_id, reason='key_rotation')`.
3. **`POST /admin/auth/logout`** (caller's own session) →
   `revoke_session(token, reason='logout')`.
4. **`POST /admin/users/:user_id/sessions/revoke`** (admin only) →
   `revoke_user_sessions(user_id, reason='admin')`.

Each revocation logs a `revoked` event per affected session.

### Audit log surface

```python
# app/db/session_events.py

EVENT_TYPES = (
    "created",
    "refreshed",       # sliding refresh (currently subsumed in rotated)
    "rotated",
    "revoked",
    "expired",
    "idle_expired",
    "used_after_revocation",
    "used_after_expiry",
)

def log_session_event(
    session_id: str,
    user_id: Optional[str],
    event_type: str,
    *,
    ip_address: Optional[str] = None,
    user_agent: Optional[str] = None,
    metadata: Optional[dict] = None,
) -> None: ...

def list_session_events(
    *,
    user_id: Optional[str] = None,
    session_id: Optional[str] = None,
    event_type: Optional[str] = None,
    limit: int = 100,
    offset: int = 0,
) -> list[dict]: ...
```

`refreshed` is currently subsumed into `rotated` since rotation
happens on every authenticated request and naturally bumps
`last_activity_at`. Kept in the event-types list for future
non-rotating refreshes.

`metadata` JSON blob. Examples:
- `created`: `{ "reason": "login" }`
- `rotated`: `{ "previous_token_hash": "<sha256 of old token>" }`
- `revoked`: `{ "reason": "role_change", "old_role": "editor",
  "new_role": "viewer" }`
- `idle_expired`: `{ "idle_minutes": 47 }`

Read API at `GET /admin/auth/session-events` (admin-only via
`requires_role("admin")` per-route guard) takes the same kwargs.

### Frontend token rotation

`frontend/src/services/api/client.ts` already wraps `fetch` and
manages auth headers. After every successful authenticated response,
read `X-New-Session-Token`; if present, call `setSessionToken(...)`
to update the stored token before the next request.

```ts
async function apiFetch<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, /* … existing auth headers … */);
  const newToken = res.headers.get('X-New-Session-Token');
  if (newToken) setSessionToken(newToken);
  // … existing response handling
}
```

Concurrent-request race: if two requests fire in parallel and both
see rotated tokens in their responses, the second one wins (last
write to localStorage). The first response's token is replaced
before it's used, so it's effectively just-in-time rotation. The
server's 5-second grace window covers any in-flight request that
was issued with the now-stale token.

If a request fails with `401` because the token was rotated and
the client missed the update, the API client retries once with the
latest stored token. Beyond one retry → escalate to logout flow.

## Data flow

```
ApiKeyMiddleware (per request)
  ├── Extract token from Authorization header (or fall back to X-API-Key)
  ├── If session token:
  │     ├── lookup_session(token, allow_grace=True)
  │     │     → match on sessions.token OR sessions.rotated_from_token (within 5s)
  │     ├── check revoked_at → 401 + log used_after_revocation
  │     ├── check absolute expiry → 401 + log expired
  │     ├── check idle expiry → 401 + log idle_expired
  │     ├── role check via required_role(method, path) + per-route guards → 403
  │     ├── rotate_session(token) → new_token
  │     │     → sessions.token = new_token, rotated_from_token = old_token
  │     │     → last_activity_at = now
  │     │     → log rotated
  │     └── set scope["state"]["principal"] = {user_id, role}
  │     └── set response header X-New-Session-Token
  └── If X-API-Key:
        ├── get_role_and_user_for_api_key(key) → (role, user_id)
        ├── role check → 403
        └── set scope["state"]["principal"] = {user_id, role}
        (no rotation; API keys are explicit credentials, not session tokens)

rbac.update_user_role / rotate_user_role
  └── revoke_user_sessions(user_id, reason)
        └── for each affected session:
              ├── set revoked_at = now, revoke_reason = reason
              └── log_session_event(session_id, user_id, 'revoked', metadata={reason, …})

POST /admin/auth/logout
  └── revoke_session(caller_token, reason='logout')

POST /admin/users/:user_id/sessions/revoke
  └── revoke_user_sessions(user_id, reason='admin')
```

## Error handling

- **401 vs 403**: 401 = not authenticated / session invalid /
  expired / revoked. 403 = authenticated but insufficient role.
  Distinct status codes; clear semantics.
- **Token rotation failures**: if the DB write to rotate fails
  (race / lock), the request still succeeds with the OLD token —
  rotation is best-effort. Next request rotates again. Log
  warning, not error.
- **Migration failure**: the new ALTER TABLE statements use
  idempotent patterns (`ADD COLUMN IF NOT EXISTS` workarounds via
  pragma checks per existing `migrations.py` pattern). Re-running
  the migration is safe.
- **Audit log write failures**: `log_session_event` swallows DB
  errors with a warning log. The session lifecycle continues; we
  prefer "session works, audit gap" over "session breaks because
  audit failed".

## Risk

- **Frontend token rotation race** — covered by the 5-second
  grace window. Acceptable.
- **Migration of existing sessions** — backfill via
  `last_activity_at = COALESCE(updated_at, created_at)`. No data
  loss. Sessions older than absolute lifetime expire on next use.
- **Bootstrap mode permanence** — currently if all DB keys are
  deleted, the system reverts to "every request passes". This
  spec preserves that behavior (still useful for first-run UX
  after `just reset`). A future hardening pass could require an
  explicit env var to enable bootstrap mode.
- **API key clients can't rotate** — explicit X-API-Key requests
  don't trigger token rotation (rotation is a session-only
  concept). Long-lived keys rotate via the existing
  `rotate_user_role` admin path. No regression vs current state.
