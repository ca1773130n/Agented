# v0.5.11 — agent_memory observability UI

**Date:** 2026-05-04
**Milestone target:** v0.5.11 (second sub-piece of E-C — production hardening / observability)
**Status:** design awaiting user review

## Context

E was decomposed into a v0.5.10 → v0.5.14 track sequenced
**C → A → B → D → E** (observability → auth → deploy → rate limit
→ backups). v0.5.10 shipped traces observability. v0.5.11 finishes
the C piece by surfacing the agent_memory tables — threads,
messages, working memory, and FTS5 recall — to operators.

The agent_memory schema already populates during agent execution,
and the silent-failure cleanup work in v0.5.2/v0.5.3 made the read
path log warnings on corruption. But operators currently have **no
way to see what an agent remembers** — no thread browser, no
working-memory viewer, no search. Closing that loop is v0.5.11.

The agent_memory API surface in `app_litestar/routes/leaf_crud_f.py`
is already complete:
- `GET /admin/agents/:id/memory/threads` — list threads
- `GET /admin/agents/:id/memory/threads/:thread_id/messages` — list messages
- `GET /admin/agents/:id/memory/working` — get working memory (markdown blob)
- `GET /admin/agents/:id/memory/recall?query=&top_k=` — FTS5 search

**Zero new backend work for v0.5.11.** Pure frontend milestone.

## Goal

Ship a per-agent observability surface for memory:

1. `/agents/:id/memory` — single stacked page with three regions:
   working memory (markdown rendered), recall search, threads list.
2. `/agents/:id/memory/threads/:thread_id` — thread detail
   (header + scrollable message list rendered via vue-styled
   `ChatBubble`).
3. Window-focus refresh (no SSE / polling) for natural "kicked off
   a run, came back" flows.
4. Read-only end to end. No edit, no delete, no thread creation.

## Non-goals

- **Edit / delete affordances.** Working memory is part of the
  agent's prompt; editing it without diff preview / undo / audit
  belongs in a dedicated tool. Thread cleanup likewise — a footgun
  during active conversations.
- **Cross-agent observability** (`/memory` standalone). Data is
  keyed by `(resource_id, resource_type)` with current routes
  scoped to `agent` only; cross-agent search is its own design.
- **Real-time SSE updates.** Memory accumulates *between* runs, not
  during one execution. Window-focus refresh captures the natural
  flow without backend SSE work. (Compare v0.5.10's traces, where
  spans accumulate during one run — different problem, different
  answer.)
- **Vector / hybrid recall** (`vector_recall` / `hybrid_recall` in
  `db/agent_memory.py`). Just FTS5 for v0.5.11; semantic surfaces
  are v0.5.11.x candidates.
- **Thread creation UI.** Operators don't create threads; agents do.
- **Memory config page.** The `GET / PUT /admin/agents/:id/memory/config`
  routes already exist (verified in v0.5.3 silent-failure cleanup);
  config editing is its own concern.

## Component design

### `agentMemoryApi`

```ts
export interface MemoryThread {
  id: string;
  resource_id: string;
  resource_type: string;  // 'agent' | 'super_agent' | etc.
  title: string | null;
  created_at: string;
  updated_at: string;
  metadata?: Record<string, unknown> | null;
}

export interface MemoryMessage {
  id: string;
  thread_id: string;
  role: 'user' | 'assistant' | 'system' | 'tool' | string;
  content: string;
  type: string;
  metadata?: Record<string, unknown> | null;
  created_at: string;
}

export interface WorkingMemory {
  entity_id: string;
  entity_type: string;
  content: string;
  content_parsed?: Record<string, unknown> | null;
  template?: string | null;
  updated_at?: string;
}

export interface RecallResult extends MemoryMessage {
  /** Optional score returned by FTS5 ranking (BM25). */
  score?: number;
}

export const agentMemoryApi = {
  listThreads(agentId, params?): Promise<{ threads: MemoryThread[] }>,
  getMessages(agentId, threadId): Promise<{ messages: MemoryMessage[] }>,
  getWorkingMemory(agentId): Promise<WorkingMemory | null>,
  recall(agentId, query, topK?): Promise<{ results: RecallResult[] }>,
};
```

REST shapes mirror what the backend returns; the component layer
unpacks `result.threads` / `result.messages` etc. The
`getWorkingMemory` returns `null` on 404 (the entity may have no
working memory yet) — we catch the 404 in the wrapper and return
`null` rather than throwing.

### `useFocusRefresh`

```ts
export function useFocusRefresh(
  fn: () => void | Promise<void>,
  opts?: { immediate?: boolean },
): void
```

Registers a `visibilitychange` listener; calls `fn` when
`document.visibilityState` becomes `'visible'`. Auto-removes the
listener on `onUnmounted`. If `immediate` is true, calls `fn` once
on mount.

### `WorkingMemoryView`

Props: `content: string | null`, `loading?: boolean`, `error?: string | null`.

Renders `renderMarkdown(content)` via existing `useMarkdown`
helpers. Empty state when `content` is null or empty. Error state
with retry slot.

### `RecallSearch`

Props: `agentId: string`. Internal state: `query`, `topK` (5/10/20),
`results: RecallResult[]`, `loading`, `error`. Submit fires
`agentMemoryApi.recall(agentId, query, topK)`. Each result row:

```
[role] · [created_at relative]
Truncated content (first 200 chars)…
[View thread →]   ← router-link to /agents/:id/memory/threads/:thread_id
```

Empty state when `query` is blank. "No matches" state when
`results.length === 0` after a successful query. Loading state
during the request.

### `ThreadList`

Props: `agentId: string`. Loads threads via
`agentMemoryApi.listThreads(agentId, { limit, offset })`. Each row:

```
[title or "(untitled)"]    [resource ref]    [updated_at relative]    [N messages]
```

Click row → router push to thread detail. Pagination at the bottom
(offset/limit 50; threads.length used to compute next/prev
disabled).

### `MessageList`

Props: `messages: MemoryMessage[]`. Renders each as
`@ai-accounts/vue-styled ChatBubble` with `:role`, `:content`,
`:timestamp` props. Wrapper div allows scrolling on overflow.

### `MemoryPage` (`/agents/:id/memory`)

Three regions stacked. Each region holds its own loading/error
state. The page orchestrator:

1. On mount, fires three independent fetches in parallel:
   - `agentMemoryApi.getWorkingMemory(agentId)`
   - `agentMemoryApi.listThreads(agentId)`
   - (no fetch for recall — search is user-initiated)
2. `useFocusRefresh` re-fires the working memory + threads fetches
   when the window regains focus. Recall results stay since the
   user's search is sticky.
3. Header shows agent breadcrumb + manual "Refresh" button (also
   triggers the two fetches).

Error in one region does not break the others.

### `ThreadDetailPage` (`/agents/:id/memory/threads/:thread_id`)

1. Loads thread metadata + messages on mount via
   `agentMemoryApi.getMessages(agentId, threadId)`. Thread metadata
   comes from a side-fetch of `getThread` (route exists; spec adds
   to the API client).
2. Header: title, resource ref, created_at, message count.
3. Body: `MessageList` with all messages.
4. "← Back to Memory" link in header.
5. `useFocusRefresh` re-loads the messages on focus (new messages
   may have arrived if the agent ran in another tab).

## Data flow

```
MemoryPage (/agents/:id/memory)
  ├── parallel fetches on mount:
  │     ├── agentMemoryApi.getWorkingMemory(agentId)
  │     │     → GET /admin/agents/:id/memory/working
  │     │     → renders in WorkingMemoryView
  │     └── agentMemoryApi.listThreads(agentId, {limit, offset})
  │           → GET /admin/agents/:id/memory/threads
  │           → renders in ThreadList
  ├── RecallSearch self-manages:
  │     → GET /admin/agents/:id/memory/recall?query=&top_k=
  └── useFocusRefresh(re-fetch working + threads)

ThreadDetailPage (/agents/:id/memory/threads/:thread_id)
  ├── on mount:
  │     ├── agentMemoryApi.getThread(agentId, threadId)
  │     │     → GET /admin/agents/:id/memory/threads/:thread_id
  │     └── agentMemoryApi.getMessages(agentId, threadId)
  │           → GET /admin/agents/:id/memory/threads/:thread_id/messages
  └── useFocusRefresh(re-fetch messages)
```

## Error handling

- REST errors: existing `handleApiError` toast pattern.
- 404 on `getWorkingMemory`: returns `null` (component shows empty
  state). Other 404s (thread detail) show "not found" empty state
  with a back-link.
- FTS5 query errors: backend's existing `try/except Exception:
  logger.warning(...)` wrap in `recall_messages` returns an empty
  list (verified in v0.5.2 silent-failure audit). UI shows the
  "no matches" state.
- Markdown rendering: `renderMarkdown` is forgiving (returns
  HTML-escaped string on parse failure); no special handling.
- Corrupt JSON metadata on messages/threads: backend's
  `_row_with_json_metadata` warning fires (v0.5.2 audit) and the
  field is silently `null` in the response. UI never crashes on
  metadata; fields are optional.

## Risk

- **Markdown XSS** — `renderMarkdown` is the same helper used in 11
  chat pages post-v0.5.9; it sanitizes via `marked` + the existing
  `useMarkdown` configuration. No new attack surface.
- **Thread list scaling** — `listThreads` returns up to `limit`
  threads; with default 50 and offset pagination, big agents are
  fine. If `memory_threads` grows enormous per agent, consider
  adding an index on `(resource_id, resource_type, updated_at
  DESC)` — but only if `EXPLAIN QUERY PLAN` shows a scan. v0.5.11
  ships without that index unless smoke surfaces a slow query.
- **FTS5 index health** — `recall_messages` already wraps FTS5
  errors per v0.5.2 audit. UI shows "no matches" on FTS errors,
  which is misleading vs "search system broken". Acceptable for
  v0.5.11; a dedicated "search degraded" toast is a v0.5.11.x
  candidate.

## Success criteria

1. `/agents/:id/memory` renders the three regions, each with its

2. Window-focus event re-fetches working memory + threads.
3. Recall search returns matching messages and "View thread" links

4. `/agents/:id/memory/threads/:thread_id` renders the thread

5. Verification triplet green; coverage gate holds.
