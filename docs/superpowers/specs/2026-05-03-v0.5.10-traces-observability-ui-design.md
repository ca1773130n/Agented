# v0.5.10 — Traces observability UI

**Date:** 2026-05-03
**Milestone target:** v0.5.10 (first sub-piece of E — production hardening)
**Status:** design awaiting user review

## Context

E was originally umbrella'd as 5 independent subsystems (auth depth,
deploy story, observability, rate limiting, backups). Decomposed
into a v0.5.10 → v0.5.14 track sequenced **C → A → B → D → E**.
v0.5.10 is **C: observability**, narrowed to **traces only** —
agent_memory observability is v0.5.11.

The `traces` and `trace_spans` tables already populate during agent
execution. The silent-failure cleanup work (v0.5.2/v0.5.3) made the
tracing write path log warnings on corruption. But operators
currently have **no way to see traces** — no UI, no list, no detail.
Closing that loop is the v0.5.10 goal.

## Goal

Ship a standalone observability surface for traces:

1. `/traces` list page — reverse-chronological list of recent
   traces with filter + pagination + aggregate stats header.
2. `/traces/:id` detail page — header (trace metadata) + span tree
   (recursive collapsible nodes built from `parent_span_id`).
3. Live updates while a trace is `running` — SSE-driven, falls back
   to historical-only when the trace is `completed` / `error`.
4. Backend SSE route addition — the only backend work in v0.5.10.

## Non-goals

- Per-entity tabs on `/agents/:id` etc. — additive cross-link,
  post-v0.5.10. The standalone list pattern lands first; cross-links
  are a follow-up that takes ~1 hour once the standalone surface
  exists.
- Server-side full-text search across span content. v0.5.10's filter
  bar is client-side text-search over the current page. Server-side
  search lands in v0.5.11 once the agent_memory search composable
  exists (FTS5 already populates `memory_messages_fts`).
- Trace deletion UI. The DELETE route exists; operator-driven
  cleanup belongs in a dedicated maintenance tool, not the
  observability surface.
- Waterfall timeline. Collapsible tree handles big traces well; the
  waterfall is a v0.5.10.x or later upgrade once we see real trace
  shapes.
- agent_memory observability. v0.5.11.

## Component design

### `TracesPage.vue` (list)

- Header card: aggregate stats from `GET /admin/traces/stats`
  (total / completed / errors).
- Filter bar:
  - Status dropdown (running / completed / error / all)
  - Entity type dropdown (agent / super_agent / team / all)
  - Text-search input (client-side filter on the current page —
    server-side search is v0.5.11)
- Trace list (`v-for` over `TraceListItem`).
- Pagination: offset-based, 100 per page, total from
  `GET /admin/traces/?count=...` (the backend already returns
  `total`).
- Empty state, loading state, error state.

### `TraceListItem.vue`

Each row:
- Trace name (linked to detail)
- Entity reference (`<entity_type>:<entity_id>`)
- Status badge (running/completed/error)
- Started_at relative time (e.g., "5m ago")
- Duration (`duration_ms`) or "running" indicator
- Span count

### `TraceDetailPage.vue`

Two-region layout:

**Header region** (top):
- Trace name + entity
- Started/finished timestamps + duration
- Status badge
- Output (when completed) or `error_message` (when error)
- `attributes` JSON, pretty-printed in a collapsible block

**Span tree region** (below):
- Recursive `SpanTreeNode` rooted at every span with
  `parent_span_id == null`
- Tree built once from `GET /admin/traces/:id` (returns trace +
  full span list); when the trace is `running`, `useTraceStream`
  opens SSE and patches the tree as events arrive
- When trace is `completed` / `error`, SSE is not opened — historical
  fetch is sufficient

### `SpanTreeNode.vue`

Self-recursive component. Each node:
- Span name + `span_type` badge (`AGENT_RUN` / `EXECUTION` /
  `TOOL_CALL` / `GENERIC` / `REASONING` / etc.)
- Status badge
- Duration
- Caret to expand/collapse children
- Expanded body: input / output / attributes / metadata
  (each pretty-printed JSON in a collapsible block)
- Children rendered as nested `SpanTreeNode`s

### `useTraceStream.ts`

```ts
export function useTraceStream(traceId: Ref<string>): {
  events: Readonly<Ref<TraceStreamEvent[]>>
  status: Readonly<Ref<'idle' | 'connecting' | 'open' | 'closed' | 'error'>>
  start: () => void
  stop: () => void
}
```

- Consumes `GET /admin/traces/:id/stream` (SSE).
- Three event kinds (one each per discriminator):
  - `span_started` — full new span object
  - `span_ended` — span_id + finished_at + duration_ms + status +
    output
  - `trace_ended` — trace_id + finished_at + duration_ms + status +
    output / error_message
- Reconnect on error with exponential backoff (cap 30s).
- Auto-stop after 5 min if trace status is still `running`
  (operator can manually re-open).

## Backend SSE route

```python
@get("/{trace_id:str}/stream", media_type="text/event-stream", sync_to_thread=False)
def stream_trace(trace_id: str) -> Stream:
    """
    SSE endpoint that polls the DB for span updates on the given
    trace and emits diffs as SSE frames. Polls every 1s; closes
    when the trace status becomes 'completed' or 'error', or after
    a 10-min hard timeout.

    For v0.5.10 we ship the polling-loop variant (option b in the
    brainstorm). When a second consumer of the event stream
    appears, or when polling cost matters, refactor to a process-
    local pub/sub bus (option a) by hooking the tracing.py
    end_span / update_span / end_trace write functions.
    """
```

Polling-loop pattern (sketch):

```python
async def stream_trace_events(trace_id: str):
    seen_span_ids = set()
    span_status_at = {}  # span_id -> status
    while True:
        trace = get_trace(trace_id)
        if not trace:
            yield {"event": "error", "data": json.dumps({"reason": "not_found"})}
            return
        spans = list_spans(trace_id)
        for s in spans:
            if s["id"] not in seen_span_ids:
                seen_span_ids.add(s["id"])
                span_status_at[s["id"]] = s["status"]
                yield {"event": "span_started", "data": json.dumps(s)}
            elif span_status_at.get(s["id"]) != s["status"]:
                span_status_at[s["id"]] = s["status"]
                yield {"event": "span_ended", "data": json.dumps(s)}
        if trace["status"] in ("completed", "error"):
            yield {"event": "trace_ended", "data": json.dumps(trace)}
            return
        await asyncio.sleep(1.0)
        # 10-min hard timeout enforced by route-level timeout decorator
```

The `Stream(media_type="text/event-stream")` pattern is the same as
the existing 10 SSE routes (e.g., the conversation streaming routes
in `leaf_crud_*.py`).

## Data flow

```
TracesPage
  → tracingApi.list({status, entityType, limit, offset})
    → GET /admin/traces/?...
  → tracingApi.stats({entityType})
    → GET /admin/traces/stats?...

TraceDetailPage
  → tracingApi.get(traceId)
    → GET /admin/traces/:id  (returns {trace, spans})
  → useTraceStream(traceId).start()  // when trace.status === 'running'
    → EventSource('/admin/traces/:id/stream')
    → patches local span tree on each event
```

## Error handling

- REST errors: existing `handleApiError` toast pattern from
  `frontend/src/services/api/error-handler.ts`. 404 on detail page
  shows a clean "trace not found" empty state with a back-to-list
  link.
- SSE errors: reconnect with exponential backoff (1s, 2s, 4s, 8s,
  16s, 30s cap). After 5 min of being unable to connect, switch to
  polling-fallback (REST refetch every 5s) until the page unmounts.
- Data corruption: if a span's `attributes` / `input` / `output`
  fail to parse as JSON, the detail node renders the raw string and
  shows an inline "couldn't parse this field as JSON" hint. (The
  silent-failure cleanup work in v0.5.2/v0.5.3 already log-warned
  on the backend; the UI just doesn't crash.)

## Risk

- **SSE polling cost** — 1s DB poll per open connection. With many
  operators watching live traces simultaneously, the load adds up.
  Mitigation: 5-min auto-stop; will revisit when usage warrants
  pub/sub bus (option a).
- **Trace volume** — if `traces` table grows large, `GET
  /admin/traces/?limit=100` may be slow without an index on
  `started_at DESC`. Quick verification: `EXPLAIN QUERY PLAN` on
  the existing list query. If slow, add the index in v0.5.10
  (one-line migration).
- **Frontend coupling** — `TraceDetailPage` is two-region with the
  span tree growing potentially deep. We've kept `SpanTreeNode`
  self-recursive and stateless beyond expand/collapse so each node
  stays under 100 LoC.
