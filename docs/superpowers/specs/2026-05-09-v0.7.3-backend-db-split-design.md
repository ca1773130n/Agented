# v0.7.3 — Backend DB Layer Split

## Goal

Split three monolithic `backend/app/db/*.py` modules into focused per-domain files, identified by the v0.7.0 `/understand` knowledge graph as the worst structural offenders.

## Targets

| File | Lines | Issue |
|---|---|---|
| `backend/app/db/triggers.py` | 1433 | 5 distinct domains (trigger CRUD / paths / GitHub repos / execution logs / PR reviews) |
| `backend/app/db/schema.py` | 2300 | Single 2300-line `create_fresh_schema()` function |
| `backend/app/db/migrations.py` | 4878 | 116 migrations + runner infrastructure all in one file |

## Strategy: file-level splits, **public API preserved**

All current public function names stay reachable from their original import paths (`from app.db.triggers import create_trigger`, etc.) via re-exports. Internal callers can migrate at their leisure. Tests must still pass without touching test imports.

### 1. `triggers.py` → 4 modules

```
backend/app/db/
  triggers.py            # trigger CRUD + prompt template history (was lines 174-526, 777-825)
  trigger_paths.py       # paths + symlinks + GitHub repos + project links (was 528-776)
  execution_logs.py      # execution log CRUD + stats (was 842-1188)
  pr_reviews.py          # PR review tracking (was 1190-end)
```

`triggers.py` re-exports the moved symbols for backward compatibility:
```python
from .trigger_paths import (

    get_symlink_paths_for_trigger, list_paths_for_trigger,

    add_project_to_trigger, remove_project_from_trigger,
    get_paths_for_trigger_detailed,

from .execution_logs import (

from .pr_reviews import (
```

### 2. `schema.py` → modular per-domain DDL

```
backend/app/db/
  schema.py              # public entry: create_fresh_schema(conn) — calls each submodule
  schema/
    __init__.py
    _core.py             # triggers, project_paths, execution_logs, prompt_snippets, trigger_template_history, pr_reviews
    _agents.py           # agents, agent_conversations, agent_memory tables
    _skills.py           # user_skills
    _orgs.py             # teams, team_members, team_agent_assignments, products, projects, project_teams
    _plugins.py          # plugins, plugin_components, marketplaces, marketplace_plugins
    _workflows.py        # workflow_executions, workflow_node_executions, workflow_*
    _security.py         # users, sessions, api_keys, password_resets, rbac, secrets, scope_filters
    _monitoring.py       # audit, monitoring_*, analytics, performance metrics
    _triggers_infra.py   # mcp_servers, webhook_dedup_keys, trigger_events
    _super_agents.py     # super_agent_*
    _setup.py            # setup_executions, bot_templates, bot_pipes
    _embeddings.py       # chunked_executions, memory_embeddings
    _misc.py             # remaining tables that don't fit a domain
```

`create_fresh_schema(conn)` becomes a thin orchestrator calling each domain function in dependency order:
```python
def create_fresh_schema(conn):
    from .schema._core import create_core_tables
    from .schema._agents import create_agent_tables
    # ... etc
    create_core_tables(conn)
    create_agent_tables(conn)
    # ...
```

Each domain function applies its CREATE TABLE / CREATE INDEX statements identically to today; **zero DDL changes**.

### 3. `migrations.py` → version-bucketed

```
backend/app/db/
  migrations.py          # public entry: run_migrations() + VERSIONED_MIGRATIONS list (now imports buckets)
  migrations/
    __init__.py
    _runner.py           # run_migrations, _mark_stale_executions, helpers
    v04_initial.py       # migrations 1-50 (v0.2.x → v0.4.x consolidation)
    v05_features.py      # migrations 51-100 (v0.5.x track)
    v06_features.py      # migrations 101-115 (v0.6.x track)
    v07_features.py      # migrations 116+ (v0.7.x track)
```

`migrations.py` becomes:
```python
from .migrations._runner import run_migrations, _mark_stale_executions
from .migrations.v04_initial import V04_MIGRATIONS
from .migrations.v05_features import V05_MIGRATIONS
from .migrations.v06_features import V06_MIGRATIONS
from .migrations.v07_features import V07_MIGRATIONS

VERSIONED_MIGRATIONS = (
    V04_MIGRATIONS + V05_MIGRATIONS + V06_MIGRATIONS + V07_MIGRATIONS
)
```

Each `vXX_*.py` file owns its migration functions + a `VXX_MIGRATIONS = [(version, name, fn), ...]` tuple list.

## Risks

- **Circular imports:** schema submodules must not import each other; everything goes through `schema.create_fresh_schema()`.
- **Migration registration order:** version numbers must remain monotonic across all bucket files when concatenated. Validation test asserts strictly-increasing version IDs.
- **Test discovery:** ensure pytest still finds `tests/test_migration_*.py` — those reference migration functions by name; preserve names exactly.
- **AGENTED_LITESTAR_SKIP_STARTUP** path: `lifecycle.py` calls `run_migrations()` from `app.db.migrations`. Keep that import path working.

## Tests

- `test_migration_path.py` (existing) — full migration applies cleanly
- `test_schema.py` (new) — `create_fresh_schema()` produces same table/index set as before (compare `sqlite_master` dump pre/post)
- All existing per-migration tests (`test_migration_NNN_*.py`) — must still pass

## Out of scope

- Renaming any public function
- Changing any DDL
- Touching service-layer or route-layer code (callers' import paths still work via re-exports)
- Moving the `agent_memory.py`, `connection.py`, `ids.py`, etc. — only the 3 named monoliths in this spec

## Verification

2. `cd backend && uv run pytest tests/test_migration_path.py tests/test_schema.py` targeted
3. `just build` — frontend untouched, but verifies Python imports compile
