# v0.5.14 — Rate limiting (design)

E-D piece. Extend the existing `RateLimitMiddleware` to cover all
`/api/*` and `/admin/*` routes, with per-API-key (or per-user)
keying when authenticated and per-IP fallback otherwise. Defaults
are env-var tunable; sensitive endpoints (login, install) get
tighter overrides via a new `requires_rate_limit` guard.

## Goals

- Prevent abuse of `/api/*` and `/admin/*` mutating endpoints
  without breaking normal operator usage (60/min on GETs, 30/min
  on writes is generous for a single-operator tool but stops
  runaway loops).
- Anti-bruteforce on `POST /api/auth/login`, `signup`,
  `forgot-password`, `reset-password` (5/min/IP).
- Anti-DoS on subprocess-install routes (10/hour/key).
- Keep operator visibility: 429 response carries `Retry-After`
  header (existing behavior); event audited via existing logger.
- Configurable without redeploy: env vars override hard-coded
  defaults.

## Non-goals

- Distributed rate limiting (Redis, etc.). workers=1 keeps the
  in-memory `_FixedWindowLimiter` safe.
- Token bucket / sliding window. Fixed window is enough for
  v0.5.14.
- Operator-tunable runtime config (env-var redeploy is fine).
- Per-user UI to view current consumption.

## Architecture

```
Layer 1 — coarse defaults
  app_litestar/middleware.py:_RATE_LIMITS table
    extended to cover all /api/* and /admin/* by method.

Layer 2 — per-route overrides
  app_litestar/rate_limit_guard.py
    requires_rate_limit(limit, window) — Litestar guard factory
    plus a path-keyed overrides registry that the middleware
    consults BEFORE the coarse table.

Layer 3 — keying
  app_litestar/middleware.py:_resolve_rate_key(scope)
    Reads scope["state"]["principal"]["user_id"] (set by
    ApiKeyMiddleware in v0.5.12). Falls back to per-IP.

Layer 4 — config
  scripts/check_env.py adds 4 new OPTIONAL_VARS:
    RATE_LIMIT_API_GET_PER_MIN (default 60)
    RATE_LIMIT_API_WRITE_PER_MIN (default 30)
    RATE_LIMIT_ADMIN_PER_MIN (default 30)
    RATE_LIMIT_LOGIN_PER_MIN (default 5)
  .env.example documents them.
```

## Components

### Middleware extensions (`app_litestar/middleware.py`)

The current `_RATE_LIMITS` is a tuple of `(prefix, limit, window)`.
Extend to a list of `(method, prefix, limit, window)` so HTTP
method matters. The current generic-webhook special case (`POST /`,
`20/10s`) and GitHub webhook (`/api/webhooks/github`, `30/min`)
stay; they sort first.

New default rows added:
- `(GET, /api/, RATE_LIMIT_API_GET_PER_MIN, 60.0)`
- `(POST|PUT|PATCH, /api/, RATE_LIMIT_API_WRITE_PER_MIN, 60.0)`
- `(DELETE, /api/, RATE_LIMIT_API_WRITE_PER_MIN/2, 60.0)` — half of write limit
- `(*, /admin/, RATE_LIMIT_ADMIN_PER_MIN, 60.0)`

A wildcard method (`*`) means apply to all methods that prefix-match.

`_RATE_LIMITS` is computed at module load from env vars + defaults
so the table remains a single source of truth.

`_resolve_rate_key(scope) -> tuple[str, str]` returns
`("user", user_id)` if `scope["state"]["principal"]["user_id"]`
is set, else `("ip", client_ip)`. Used as the limiter's key prefix.

`RateLimitMiddleware.handle` now:
1. Checks the per-route overrides registry (Layer 2) first.
2. Falls through to `_RATE_LIMITS` if no override matches.
3. Resolves rate key via `_resolve_rate_key`.
4. Returns 429 + `Retry-After` if `_limiter.hit(...)` returns False.

The middleware is registered in `app_litestar/main.py` AFTER
`ApiKeyMiddleware` so the principal is already in scope state.

### Guard factory (`app_litestar/rate_limit_guard.py`)

```python
# Module-level registry — populated by requires_rate_limit() at
# import time. Middleware reads this on every request.
_PER_ROUTE_OVERRIDES: dict[tuple[str, str], tuple[int, float]] = {}

def requires_rate_limit(limit: int, window_seconds: float):
    """Litestar guard factory. Registers a per-route limit at import
    time and returns a no-op guard (the actual enforcement happens
    in RateLimitMiddleware via the registry)."""
    def guard(connection, _route_handler) -> None:
        return  # enforcement is in middleware
    # Register the path + method here. The path is read from the
    # route handler's metadata at registration time, but that's a
    # Litestar internal — see implementation note below.
    return guard
```

**Implementation note**: Litestar guards are functions, not
class-bound, so the guard factory doesn't know its route's path at
registration time. The registry is populated indirectly: each
`@post("/path", guards=[requires_rate_limit(5, 60)])` will produce
a guard that, on first invocation, registers itself with
`(method, path)` from the connection. After the first request to
that route, the override is cached and subsequent requests get the
right limit.

This is acceptable because:
- The first request goes through the middleware's coarse default,
  which is more permissive than any override → no false 429.
- Subsequent requests use the cached override.
- A 1-request window where coarse rules apply is operationally
  equivalent to a brief startup race; acceptable at this scope.

Alternative: walk Litestar's route registry at app startup and
populate `_PER_ROUTE_OVERRIDES` directly. Cleaner but requires
hooking into the on_startup lifecycle. Deferred to follow-up.

### Env-var defaults (`scripts/check_env.py`)

Add to `OPTIONAL_VARS`:
- `RATE_LIMIT_API_GET_PER_MIN` (default 60)
- `RATE_LIMIT_API_WRITE_PER_MIN` (default 30)
- `RATE_LIMIT_ADMIN_PER_MIN` (default 30)
- `RATE_LIMIT_LOGIN_PER_MIN` (default 5)

`.env.example` documents each with a one-line description.

`middleware.py` reads them via `int(os.environ.get(NAME, DEFAULT))`
at module load.

### Per-route overrides applied

| Route | Limit | Window |
|---|---|---|
| `POST /api/auth/login` | 5 | 60s |
| `POST /api/auth/signup` | 5 | 60s |
| `POST /api/auth/forgot-password` | 3 | 60s |
| `POST /api/auth/reset-password` | 5 | 60s |
| `POST /api/setup/bundle-install` | 10 | 3600s |
| `POST /admin/backends/{id}/install` | 10 | 3600s |

Login + signup get 5/min/IP (peak human typo recovery). Forgot
password is 3/min/IP because it triggers email side-effects.
Subprocess installs are 10/hour/key because each one launches a
multi-second process.

## Data flow

```
Request arrives
  │
  ▼
ApiKeyMiddleware (existing, v0.5.12)
  - authenticate
  - role check
  - rotate session token
  - stash principal in scope["state"]
  │
  ▼
RateLimitMiddleware (extended)
  1. Per-route overrides registry?
     - Yes → use that (limit, window)
     - No  → match _RATE_LIMITS table; first method+prefix wins
  2. Resolve key:
     - principal.user_id → ("user", user_id)
     - else              → ("ip", client_ip)
  3. _limiter.hit(key + path, limit, window)
     - allow → continue
     - deny  → 429 + Retry-After
  │
  ▼
Route handler
```

## Error handling

- 429 response shape unchanged: JSON body `{"error": {"code":
  "RATE_LIMITED", "message": "Rate limit exceeded"}, "request_id":
  "..."}` with `Retry-After: <window>` header. (Already correct in
  existing middleware; preserved.)
- Misconfigured env var (e.g., `RATE_LIMIT_API_GET_PER_MIN=abc`)
  → middleware falls back to default + logs WARNING.
- Per-route override registration race (first-request edge): no
  user-visible error; coarse default applies for one request.

## Testing

`backend/tests/test_rate_limit_v2.py` — ~10 tests:
1. Per-IP rate limiting on unauthenticated route (login).
2. Per-API-key rate limiting on authenticated route (e.g., GET
   `/api/agents`).
3. Different API keys get separate budgets on the same route.
4. Same API key from different IPs shares a budget (key wins).
5. Per-route override (login=5/min) is tighter than coarse default.
6. 429 response has `Retry-After` header.
7. 429 response body shape includes `error.code = RATE_LIMITED`.
8. Webhook routes preserve their existing limits (regression).
9. Health endpoints are NOT rate-limited (regression).
10. Env-var override (`RATE_LIMIT_API_GET_PER_MIN=2`) is honored.

## Conventions

- Rate-limit constants live in `middleware.py` next to `_RATE_LIMITS`.
- Per-route guards live in `rate_limit_guard.py`.
- Env-var documentation in `check_env.py:OPTIONAL_VARS` is
  authoritative; `.env.example` echoes it.
- Test file lives in `backend/tests/test_rate_limit_v2.py` (the
  `_v2` suffix because there's a pre-existing `test_rate_limit.py`
  for the legacy fixed-window logic).

## Out of scope

- Redis-backed limiter (workers=1 makes it unnecessary).
- Operator UI for current limits / consumption.
- Token-bucket or sliding-window algorithms.
- Per-resource limits (e.g., per-project quota).
