# v0.5.13 — Deploy story (design)

E-B piece. Make Agented production-deployable on (a) a single host
(macOS or Linux) and (b) a container runtime, with a runbook,
operator tooling, and a CI/CD release workflow that produces a
versioned Docker image.

## Goals

- An operator with a fresh clone can stand up production Agented in
  ≤ 15 minutes following only `docs/deploy/RUNBOOK.md`.
- Required environment variables are documented in `.env.example`
  and validated at startup — the process refuses to start with a
  clear message naming the missing variable rather than booting in a
  silently-degraded state.
- Both deploy targets share the same image of "configured":
  `.env` file is canonical; Keychain/Docker-secrets are optional
  layers that resolve INTO `.env`-style variables.
- A `just deploy-prod` recipe replaces the existing `just deploy`
  for production posture (the dev recipe stays in place under the
  current name).
- CI builds and pushes a tagged Docker image on every git tag
  matching `v*`.

## Non-goals

- Multi-host orchestration (Kubernetes, Nomad). Single replica only;
  workers=1 is enforced by current in-memory SSE state.
- Hosted SaaS posture. This is operator-deployed software.
- Auto-scaling, load balancing, blue/green deploys.
- Migration from existing `just deploy` for dev — that recipe
  continues to be the dev path.

## Architecture

Four layered deliverables, each independently shippable:

```
Layer 1 — Hygiene & runbook
  docs/deploy/RUNBOOK.md     production cold-start procedure
  .env.example               required + optional vars (commented)
  scripts/check_env.py       startup validator; CLI + library
  docs/deploy/SECRETS.md     extends docs/SECURITY.md to keychain + docker secrets

Layer 2 — Single-host tooling
  justfile                   deploy-prod, healthcheck recipes
  scripts/healthcheck.py     standalone CLI; exit nonzero on red
  scripts/launchd/com.agented.backend.plist
  scripts/launchd/com.agented.sidecar.plist
  scripts/systemd/agented-backend.service
  scripts/systemd/agented-sidecar.service
  scripts/systemd/INSTALL.md (or inline in RUNBOOK)

Layer 3 — Container tooling
  Dockerfile                 multi-stage; backend wheel + frontend dist
  docker-compose.yml         backend + sidecar (frontend served by backend)
  .dockerignore
  justfile                   docker-build, docker-up, docker-down, docker-logs

Layer 4 — CI/CD release
  .github/workflows/release.yml   triggered on tag push; builds image, pushes to GHCR
```

## Components

### Layer 1 — Hygiene & runbook

**`scripts/check_env.py`** — single source of truth for required vs
optional env vars. Exposes:
- `REQUIRED_VARS` and `OPTIONAL_VARS` constants (lists of dicts:
  `{"name", "description", "example", "secret": bool}`)
- `validate(strict=True)` — returns `(ok: bool, missing: list[str], warnings: list[str])`.
- CLI: `python -m scripts.check_env` exits 1 with a formatted
  table on missing required vars; exits 0 with warnings printed to
  stderr otherwise.

Required (production): `AGENTED_API_KEY` (or `AGENTED_API_KEY_FILE`
pointing to a secrets-mounted file), `AI_ACCOUNTS_API_KEY` (same),
`AI_ACCOUNTS_VAULT_KEY`, `AGENTED_ENV=production`.

Optional with defaults: `LOG_LEVEL`, `GUNICORN_BIND`, `VITE_HOST`,
`VITE_ALLOWED_HOSTS`.

The validator hooks into the gunicorn lifecycle via
`gunicorn.conf.py`'s `on_starting` and the sidecar's startup. On
failure: log the missing var list, exit nonzero.

**`.env.example`** — every var from `check_env.py:REQUIRED_VARS +
OPTIONAL_VARS` with a one-line description, an example value (NEVER
a real secret), and a marker (`# SECRET — do not commit`) for
secret-bearing vars.

**`docs/deploy/RUNBOOK.md`** — the cold-start runbook. Sections:
1. Prerequisites (Python 3.10+, Node 18+ via mise, `just`, `uv`)
2. Clone + initial setup (`bash scripts/setup.sh`)
3. Provision secrets (three subsections: macOS Keychain extension,
   `.env` file approach, Docker secrets)
4. Validate (`just check-env`)
5. Single-host start (`just deploy-prod`)
6. Container start (`just docker-up`)
7. Healthchecks (`just healthcheck`, what each component reports)
8. Rotation + upgrade procedure
9. Rollback

**`docs/deploy/SECRETS.md`** — extends `docs/SECURITY.md` to cover
the Docker-secrets pathway (mounted secret files at
`/run/secrets/<name>`, env-var redirect via `*_FILE` convention).

### Layer 2 — Single-host tooling

**`just deploy-prod`** — production deploy recipe, distinct from
`just deploy` (which stays as dev). Steps:
1. Run `just check-env`; abort on failure.
2. Build frontend (`just build`).
3. Stop any existing instance (`just kill`).
4. Start sidecar in background, wait for `/health` 200.
5. Start gunicorn with `--daemon` so it survives the shell.
6. Print PID files + log file paths.
7. Optional `--no-daemon` flag for foreground.

**`scripts/healthcheck.py`** — standalone CLI. Probes:
- Backend `:20000/health/liveness` — 200?
- Backend `:20000/health/readiness` — 200 + DB ok + scheduler ok?
- Sidecar `:20001/health` — 200?
Returns 0 on all-green, 1 with structured stderr otherwise.

**`scripts/launchd/com.agented.backend.plist`** — macOS launchd
template. Loads on session login; runs gunicorn under the operator's
UID. Operator copies to `~/Library/LaunchAgents/` and runs
`launchctl load`. RUNBOOK shows the inline customization steps
(paths, env-var sourcing).

**`scripts/launchd/com.agented.sidecar.plist`** — analogous for the
sidecar.

**`scripts/systemd/agented-backend.service`** — Linux systemd unit
template (User-level service, not system). Operator copies to
`~/.config/systemd/user/` and runs `systemctl --user enable`.

**`scripts/systemd/agented-sidecar.service`** — analogous.

### Layer 3 — Container tooling

**`Dockerfile`** — multi-stage:
- Stage 1 (`frontend-builder`): `node:20-alpine`, install + build
  frontend. Exports `dist/`.
- Stage 2 (`backend-builder`): `python:3.10-slim`, install `uv`,
  install backend deps from `backend/pyproject.toml`. Stage caches
  the dep layer.
- Stage 3 (`runtime`): `python:3.10-slim`, copy backend source,
  copy installed deps from stage 2, copy frontend `dist/` from
  stage 1, install `gunicorn` entrypoint. Default command:
  `gunicorn -c gunicorn.conf.py`. EXPOSE 20000.

**`docker-compose.yml`** — two services:
- `agented-backend` — image built from Dockerfile, ports 20000:20000,
  reads `.env` file via `env_file:` directive, secrets-from-files
  via `*_FILE` env-var convention (e.g.,
  `AGENTED_API_KEY_FILE=/run/secrets/agented_api_key`).
- `agented-sidecar` — same image, different command
  (`python scripts/run_ai_accounts.py`), ports 20001:20001.
Frontend is served as static assets by the backend in container
mode (no separate Vite process — container ships the built `dist/`).

**`.dockerignore`** — exclude `.git/`, `node_modules/`,
`backend/.venv/`, `frontend/dist/` (rebuilt in Dockerfile),
`*.db`, `.env`, `tests/`.

**`just docker-build`, `just docker-up`, `just docker-down`,
`just docker-logs`** — thin wrappers around docker compose.

### Layer 4 — CI/CD release

**`.github/workflows/release.yml`** — single workflow:
- Trigger: `push` with tag matching `v*` (e.g., `v0.5.13`).
- Jobs:
  1. `test` — runs `npm run test:run` + `pytest` + `npm run build`.
  2. `build-image` — depends on `test`. Logs in to GHCR via
     `${{ secrets.GITHUB_TOKEN }}`. Builds the Dockerfile, tags as
     `ghcr.io/ca1773130n/agented:<tag>` AND `:latest`. Pushes both.
  3. `release-notes` — depends on `build-image`. Creates a GitHub
     Release using the tag's annotated message as the body.
- No CI on `pull_request` for v0.5.13 (deferred — operator is the
  reviewer for now; PR-level CI is a separate concern).

## Data flow

```
.env (host)                       .env (mounted)
  │                                  │
  ▼                                  ▼
single-host gunicorn          container compose
  │  ▲                              │  ▲
  │  └── check_env.py validates ────┘  │
  ▼     (refuses to start on missing)  ▼
Litestar app                     Litestar app
  │                                  │
  └── reads via os.environ ──────────┘
                  │
        plus EnvKeyVault for
        per-account secrets in DB
```

`*_FILE` convention: any var named `FOO_FILE=/path` resolves at
startup by reading the file's contents into `FOO`. Single mechanism
serves Docker secrets and any host-level secret-mount approach.
`check_env.py` handles the `*_FILE` lookup before validation.

## Error handling

- Missing required env var → `check_env.py` exits 1 with a table of
  missing variables and a pointer to `docs/deploy/RUNBOOK.md`.
- Sidecar refuses to start without `AI_ACCOUNTS_VAULT_KEY` (existing
  behavior; surfaced explicitly in the runbook).
- Healthcheck CLI exits 1 with structured JSON on stderr; `launchd`
  / systemd configs use it as their `KeepAlive`/`Restart` trigger.
- Docker compose: `restart: unless-stopped` on both services;
  `healthcheck:` directives use the in-image `scripts/healthcheck.py`
  so the orchestrator can route around failures.
- CI release workflow: a failing `test` job blocks `build-image`.

## Testing

- `scripts/check_env.py` — unit tests covering: required-var
  detection, `*_FILE` resolution, optional-var defaults, the CLI
  exit codes, and the structured-output format.
- `scripts/healthcheck.py` — unit tests using `unittest.mock` for
  `urllib.request.urlopen`; verify exit codes, structured output,
  partial-failure cases.
- `Dockerfile` — `just docker-build` runs the multi-stage build to
  completion (no full test suite in CI Docker layer; baseline build
  succeeds).
- `docker-compose.yml` — smoke test: `docker compose up -d`, wait
  for healthchecks green, `docker compose down`. Captured as
  `just docker-smoke`.
- `.github/workflows/release.yml` — verified manually by pushing a
  test tag (`v0.5.13-rc1`) to a temporary branch; the workflow's
  full success criterion is "tag → image in GHCR".
- Single-host launchd/systemd templates — operator manually
  validates per the runbook (no automated test on this layer in
  v0.5.13).

## Conventions

- Docs live in `docs/deploy/` (new directory). Existing
  `docs/SECURITY.md` stays in place; the new `SECRETS.md`
  cross-references it.
- Scripts in `scripts/` (`check_env.py`, `healthcheck.py`) and
  `scripts/launchd/`, `scripts/systemd/`. Existing scripts stay.
- Justfile recipes follow the existing `kebab-case` naming
  (`deploy-prod`, `docker-up`, `check-env`, `healthcheck`).
- Dockerfile uses official `python:3.10-slim` and `node:20-alpine`
  base images; no custom base.
- `.env.example` is the only `.env*` file checked in. `.env`,
  `.env.local`, `.env.*.local` remain gitignored.

## Out of scope

- Database backup story — that's E (v0.5.15).
- Rate limiting — that's D (v0.5.14).
- Operator UI for managing the deploy state (start/stop from the
  app's own settings page).
- Multi-region, multi-replica, or auto-scaling.
- Pull-request CI workflow (deferred; release-only CI for v0.5.13).
