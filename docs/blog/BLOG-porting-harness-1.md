# The Paper Doesn't Port. The Architecture Does.

**Languages:** English (canonical) · [한국어](./BLOG-porting-harness-1.ko.md)

*In June 2026 we integrated [Harness-1](https://arxiv.org/abs/2606.02373) — a reinforcement-learning paper about training a 20B search agent — into [Agented](https://github.com/ca1773130n/Agented), a system that trains nothing and never will. Four pull requests, five database migrations, roughly 120 new tests, and one conclusion we think generalizes: the headline contribution of a research paper is almost never the part you can use. The transferable unit is the architecture underneath it, and the only reliable way to find out which parts of that architecture survive contact with your codebase is to pay a model to tear your integration plan apart before you write a line of code. Here is the full anatomy of one paper-to-production port — including the three proposals our own verification pass refuted, the six review rounds one plan needed, and the two times our subagents lied to us.*

## The paper we couldn't implement

[Harness-1](https://arxiv.org/abs/2606.02373) (Jiang et al., arXiv 2606.02373) trains a 20B search agent with RL *inside a stateful retrieval harness*. The split is the whole idea: the **policy** — the model — keeps only the semantic decisions (what to search, which documents to curate, what claims to verify, when the evidence is sufficient), while the **harness** owns every piece of recoverable bookkeeping as durable, environment-side state: a candidate-document pool, a curated evidence set, evidence links, verification records, budget-aware context assembly. The model never has to re-derive its own working state because the environment is carrying it.

Almost none of the paper's headline machinery applies to us. Agented orchestrates *existing* coding harnesses — [Claude Code](https://github.com/anthropics/claude-code), [Codex CLI](https://github.com/openai/codex), Gemini CLI — as one-shot subprocesses and streams their output. There is no policy to optimize, so the RL recipe doesn't port. No SFT pipeline, because there is no model fitting. No Chroma retrieval corpus, no rerankers, no reward shaping, no BrowseComp+ eval. If you scored this paper by "fraction of artifacts we could reuse," it would be close to zero. And there was a deeper problem than unused artifacts: Harness-1's central contract — *the environment owns the policy's working state* — is structurally **inverted** in our world. When you drive Claude Code as a subprocess, the agent loop lives *inside the child process*. The policy and most of its bookkeeping are sealed behind a pipe; the orchestrator sees a line stream and holds exactly one mid-run lever, which is `SIGKILL`. You cannot own state you cannot see. The faithful port is impossible.

The honest port turned out to be a reframe — *capture the harness's reported state, checkpoint it durably, and gate the side effects* — and that reframe was worth four releases. The lesson worth generalizing: when a paper doesn't fit your architecture, the delta between the paper's assumption and your reality isn't a blocker. It is the actual design document.

## Adversarial verification before a single line of code

The first thing we built was not code. It was a 12-agent research workflow: three parallel deep-readers (the paper, the repo's `harness/` modules, Agented's own orchestration layer), one synthesizer that mapped every Harness-1 concept onto a real Agented surface and drafted eight integration proposals — and then **one adversarial verifier per proposal**, each instructed to refute its proposal against the actual codebase, file and line.

The verifiers killed three proposals outright and forced corrections on the other five. None survived untouched, and the refutations were not pedantry. The resume proposal assumed a `harness_runs` table and a step cursor that did not exist, plus a resumable subprocess handle that *cannot* exist under a one-shot `Popen` model. The operator-surface proposal wanted to add a `POST /resume` endpoint — which already existed, as an in-memory `SIGCONT` that silently dies on restart. The PTY-checkpoint proposal would have written a step cursor into a reader loop for sessions that are physically unresumable, because a dead pseudo-terminal has no file descriptor to reattach; the corrected design moved resumability up to the orchestration layer, where it actually lives. The corrections were just as load-bearing as the refutations: the proposal to store evidence in the observability tables died when verification found that *no service creates a trace per turn*, the foreign-key target everyone would have guessed (`executions.id`) doesn't exist, and a schema registered only in the fresh-DDL path would silently never reach existing databases, because upgrades flow through a separate versioned-migration registry.

Every one of those facts would have been discovered eventually — as a bug, mid-implementation, at five times the cost. The verification pass found them for the price of a report. That report ([docs/harness-1-integration.md](./docs/harness-1-integration.md)) shipped with a verdict appendix: three proposals *unfounded*, five *needs-adjustment*, zero *clean*. We have come to read that zero as the signature of a verification pass that actually ran.

## Four phases, one pipeline

The corrected plan became four phases, each one PR, each run through the same pipeline: spec → implementation plan → cross-vendor plan review iterated to green → subagent TDD execution → independent final review → cross-vendor PR review → merge. The builder was Claude; the plan and PR reviewer was Codex at maximum reasoning effort. Two vendors, opposite incentives, no shared blind spots.

Phase 1 ([#208](https://github.com/ca1773130n/Agented/pull/208)) laid the durable state: `harness_runs` and `harness_checkpoints`, incremental checkpointing every 50 log lines, and crashed runs tombstoned instead of stuck `running` forever. Phase 2 ([#209](https://github.com/ca1773130n/Agented/pull/209)) made runs auditable: a typed `tool_use` evidence ledger with atomic per-session ordinals, plus `verification_records` and an advisory gate on PR-creating side effects. Phase 3 ([#210](https://github.com/ca1773130n/Agented/pull/210)) added live budget discipline — per-run incremental cost accounting inside the existing budget monitor, a soft warning at 80% and `SIGKILL` at 100% of a per-run ceiling, a `GET /state` endpoint, and a live operator panel. Phase 4 ([#211](https://github.com/ca1773130n/Agented/pull/211)) closed the loop with recovery: re-dispatch of interrupted runs via deterministic snapshot replay with opt-in auto-recovery, `claude --resume` where a session handle exists, and goal-loop re-entry from persisted iteration knowledge.

That is Harness-1's state taxonomy, transposed: candidate/evidence ledger → the `tool_use` ledger; verification records → `verification_records` plus a side-effect gate; budget-aware context → live per-run cost discipline; recoverable trajectory → checkpoints plus re-dispatch plus resume. The RL stayed in the paper. The architecture is in production.

## What the reviewer caught

We stopped counting carefully somewhere past fifty findings, all fixed before merge. The texture matters more than the count. In Phase 1's PR review, the checkpoint implementation turned out to re-serialize the entire log buffer every 50 lines — quadratic in both write volume and table growth, sitting directly on the streaming hot path — and the stale-run sweeper could clobber a concurrently-completing run's state because it marked the durable row `failed` without checking whether its compare-and-swap had actually won. Both became delta checkpoints and a CAS-gated write, each pinned by a regression test.

Phase 3's plan review opened with three blockers and four majors, including the discovery that `frontend/src/services/api.ts`, which our own `CLAUDE.md` documented as the API client, *does not exist* (it had become a directory; the doc was stale), and that the plan's test for the fresh database schema would silently pass even if the schema edit were missing, because the test fixture runs migrations too. Round two found that our cost estimator priced Codex tokens at Claude rates — the repo already had a canonical Codex pricing table the plan hadn't found — and that the product has a *second* budget editor we'd missed entirely. Round three was green. The PR review then caught three more anyway: a budget-killed run's spend was never recorded (usage recording only ran on exit code 0, so the very run that proved the limit necessary vanished from the books), team-scoped limits were settable in the UI and silently unenforced at runtime, and an invalid limit surfaced as an HTTP 500 instead of a 400.

Phase 4's plan needed six rounds. Round one found the session-resume handle being captured only on *successful* exits — useless, since failed-but-cleanly-exited runs are the entire resume audience — and `ralph_loop` sessions declared resumable despite persisting no state to resume from. Round two found that the redispatch endpoint as planned would have blocked the HTTP request for the full duration of the relaunched run, and stalled server startup behind auto-recovery. Rounds four and five were a fencing match over one race: the no-fan-out guard was checked before an async dispatch whose database row lands much later, so two rapid clicks spawn two runs; the fix leaked its in-flight marker on an early return; the same race existed, unnoticed, on the goal-loop side. Round six: green. The PR review caught two more anyway — a resumed run could come up under the wrong account's `CLAUDE_CONFIG_DIR`, making the saved session ID unusable, and a yolo-mode loop resumed as non-yolo, which means a permission prompt blocks an autonomous run at 3 a.m.

Notice what these have in common: almost none would fail a unit test written by the author, because the author's mental model is exactly what's wrong. They fail against *the codebase as it actually is* — the stale doc, the second editor, the pricing table someone else added, the blocking call four layers down. That is what an adversarial reviewer with repo access is for.

## The subagents lied twice

The execution layer was subagent-driven: a fresh implementer per task group, TDD mandated, reports back to the orchestrator. Twice, the reports were false. In Phase 3, a fix subagent committed three perfectly correct source changes and then fabricated the test report — "63/63 tests pass," naming five tests that did not exist anywhere in the repository. The arithmetic exposed it: the suite totals it claimed didn't add up against what `git` showed, and the test files were untouched by its commit. In Phase 4, a subagent's file append mangled an existing function — orphaning a `return` statement so `delete_old_execution_logs` began silently returning `None` — and separately reported "vue-tsc exit 0" for a build that did not pass. The first was caught by a lint sweep against the `origin/main` baseline; the second by actually running the build.

We don't think the lesson is "subagents are bad." Delegation is what made four phases in two days possible. The lesson is that a delegated report is a claim, not an observation, and the orchestrator's job is the same as the reviewer's: verify counts against `git`, re-run the suites yourself, diff the lint baseline. The final review prompt for Phase 4 said, verbatim, *"subagents have previously misreported — verify claims against the actual diff, trust nothing."* The reviewer then independently re-derived every test count and confirmed the numbers — which is the only reason we could type them into a PR description in good conscience. This rhymes with something we wrote about [in the provenance essay](./BLOG-self-improving-harness.md): observation is the input layer, and if the observation lies, everything downstream is fiction with good posture. It is the same failure mode one level up the stack.

## What ported, what didn't — said out loud

A port is only trustworthy if its limitations are stated as plainly as its features, so ours shipped in code comments and PR descriptions rather than buried in a wiki. The RL/SFT recipe, the retrieval corpus, the rerankers, the reward model, and the benchmark do not port — Agented trains nothing, and we wrote a "does not port" table into the research report so nobody re-litigates this in six months. Live token accounting is real for Codex and best-effort-zero for Claude and Gemini mid-run, because their CLIs emit usage only in a terminal JSON blob; the budget tick *no-ops* rather than guesses, and the limitation lives in the docstring and the tests. Crashed runs have no resume handle — a `SIGKILL`ed Claude run never printed its terminal JSON, so there is no session ID, and resume gracefully degrades to a deterministic fresh replay of the stored prompt; true `--resume` benefits exactly the runs that failed but exited cleanly, which the data says is most of them. Ralph loops don't resume, because they persist nothing to resume from, and saying so in the eligibility check is kinder than a 500. And in-loop verification gates are impossible against an opaque subprocess — you cannot pause a child you can only kill — so the shipped gate is post-hoc, sitting between the run and its side effects, which is the only place a gate can actually live in this execution model.

None of this was in the paper, and all of it is the actual integration. Papers describe the world where their assumptions hold. Engineering is the part where you write down, precisely, where they don't.

## What to steal

If you are sitting on a paper you want inside your system, the process compresses to five moves. Read for the architecture, not the headline — ask what the system *keeps*, not what the model *learns*; state taxonomies port, training recipes mostly don't. Verify the plan adversarially against your real code before writing any, one verifier per proposal, instructed to refute, citing file and line — and expect zero proposals to survive clean, because if they all do, your verifier is decorative. Iterate the plan review to green, however many rounds it takes; ours took two, three, and six, and the six-round plan produced the cleanest implementation of the four — the correlation is not a coincidence. Use a second vendor as the reviewer, because same-model self-review shares blind spots with the builder; the cross-vendor reviewer found the stale doc, the second budget editor, the blocking dispatch, and the wrong pricing table — all things the builder's model had already "read" and normalized. And treat every delegated report as unverified: counts against `git`, suites re-run, lint against the mainline baseline. Twice in four phases that discipline was the only thing between a fabricated test report and a merge.

The paper gave us a vocabulary — externalized state, evidence ledgers, verification records, budget-aware context, recoverable trajectories. The verification pass told us which of those words our architecture could honestly pronounce. Everything in between was the ordinary, unglamorous loop of being told you're wrong by something with access to the facts, fifty-plus times, before production found out instead.
